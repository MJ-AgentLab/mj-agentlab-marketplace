# Domain Acquisition — 领域信息获取与特化机制

> **定位**：本文是"逐类图怎么画"（同目录 7 个 `*-diagram.md` 绘制提示词）与"某个具体领域"之间的**桥**。提示词领域无关；本文回答 **"给一个新领域（docker / python / claude-code-plugin / postgreSQL…），怎么把它的事实搜出来、归类、映射成画图输入"**。
> **自含**：本文 + 同目录 7 个 `*-diagram.md` 构成一个自洽集合；只引用同目录文件 + 外部公开来源（c4model.com / dbt 等），不依赖任何其它文档。
> **产物语义**：填完「领域画像 §2」+ 跑完「获取阶梯 §3」= 你拥有了为该领域画全部图所需的全部输入。该领域若反复使用，可据「作者配方 §7」沉淀成一份"领域特化手册"（手册应包含的内容清单见 §5.2；全局适用性矩阵见 §5.1）。

## §1 为什么需要这一层

7 张图的提示词逐类讲"怎么画"，但每个提示词的「信息获取要点」只给零散的"看哪些文件"清单，并用 **「Layer 0」** 指代"先抽的源事实"——而 Layer 0 从未被定义。结果：换一个领域，你不知道 ① 该领域有哪些"实体"、② 它们各算什么"角色"（→什么形状）、③ 去哪儿、用什么搜法挖出来、④ 哪些图对这个领域才高价值。

本文补这一层：把"画图所需信息"显式拆成 **6 类领域画像（§2）**，定义一条 **4 级事实获取阶梯（§3，正式定义 Layer 0）**，使"换领域"变成"填画像 + 跑阶梯"的机械动作。

> 一句话回顾通用框架（够用即可）：架构图压在**两轴**上——**结构缩放轴**（系统外→容器→组件→代码，即 C4 的 Context/Container/Component/Code）+ **正交轴**（行为：时序/状态机；物理：部署）。元素三分：**节点=构件、边=连接件、分组=约束**。角色原则：**一对象一角色一形状**（借 C4「抽象先于记法」）。

## §2 领域画像（Domain Profile）—— 画一个领域的图需要的 6 类信息

每画一个新领域，先把下面 6 类填出来（填它本身就是"特化"的全部内容）。本表**领域无关**：最右列只给"抽象示例"说明该类信息长什么样，**不绑定任何具体领域**；某个领域填完后的成品形态，见该领域的特化手册（沉淀配方见 §7）。

| # | 信息类别 | 喂给图的什么 | 通用问法 | 抽象示例（领域无关）|
|---|---|---|---|---|
| ① | **实体清单 + 角色→形状** | 节点（构件）| 这个域有哪些"东西"？每种算什么角色？映射成什么形状 + «stereotype»？ | 把实体按角色归类（如 源 / 中间 / 汇聚 / 信号 / 观测），每个角色固定一种 Mermaid 形状；某些实体不作节点而**作边标签**（如承载血缘的转换逻辑）|
| ② | **连接件语义** | 边 | 实体间有哪些关系？每类图里这条边读作什么？ | 该域的边读作什么（写入 / 读取 / 守卫 / 自环回…）；线型遵循方法论 §5 各图边语义；边标签承载关键语义 |
| ③ | **命名/结构自动归类杠杆** | ① 的机械判定 | 有没有命名前缀/目录结构/关键字，能"看名字就定角色"？ | 命名前缀 / 目录族 / 关键字能否机械定角色（如 `xxx_` 前缀 → 某角色、`domain/` 目录 → 某层）|
| ④ | **信息源 + 搜索式（= Layer 0）** | ①② 的事实出处 | 该域 source-of-truth 配置/代码在哪？用什么 glob/命令抽？ | 该域最权威的清单 / 配置 / 声明文件在哪，用什么 glob 或命令抽；每条画图断言对到 `file:行号` |
| ⑤ | **轴/密度判断** | 画哪些图、谁高价值 | 哪几类图信息密度高、值得做实？哪几类被"压扁"？ | 哪些图对该域高密度（做实）、哪些被压扁（轻量或略），见 §5.1 全局适用性矩阵 |
| ⑥ | **双标签身份源 + 领域范式** | 节点文案 + 复发画法 | 业务别名/规范 id 各从哪取？该域有哪些"必须这么画"的典型机制？ | 规范 id 与业务别名各从哪取（一对象一 id）；该域有哪些"必须这么画"的复发机制（典型范式）|

## §3 事实获取阶梯（L0 → L3）—— 正式定义那个悬空的 "Layer 0"

7 个提示词里反复出现的「Layer 0 重点抽」在此定义为一条**自底向上、证据驱动**的四级阶梯（结构上借"维度 + 证据源 + 判定"式事实核查；每级产出喂给 §2 对应类别）：

| 级 | 名称 | 干什么 | 产出（→§2）| 证据形式 |
|---|---|---|---|---|
| **L0** | **声明式清单扫描** | 读该域 source-of-truth 声明文件（配置/清单/DDL），枚举实体 | 实体清单（→①）| `file:行号` / config-block |
| **L1** | **结构/关系推断** | 从目录层级、import、`depends_on`、引用关系推出边与分层 | 边 + 分层（→②⑤）| 引用点 `file:行号` |
| **L2** | **命名约定自动归类** | 用前缀/关键字/目录族把实体机械归类成角色 | 角色赋值（→①③）| 命名规则 + 命中样例 |
| **L3** | **HITL 补缺** | 仅就 L0–L2 **挖不到**的（运行时语义、同步/异步、为何如此设计）问人 | 缺口字段 | 用户答复 |

**铁律**：每个进图的节点/边都要能追到 L0–L2 的**证据**（`path:行号` / config 块 / frontmatter）；挖不到再走 L3，**不臆造**。L3 只问"源里读不出来的"（典型：边是同步还是异步、状态是否可达、HITL 卡点）。

## §4 四域 source-map（L0/L1/L2 该去哪搜）

下表给出**四个领域并列的落地实证**，作为"换域时照着加一行"的参照（四行均为对等示例，无主次）：

| 域 | 主要实体类型 | L0 声明源（glob/命令）| L1 关系源 | L2 归类杠杆 |
|---|---|---|---|---|
| **postgreSQL** | 表(按角色)/函数/触发器/信号表/schema | `sql/**/V*.sql`·`R*.sql` DDL；`cron.schedule(...)`；`dblink(...)` | `etl_*` 函数体的 INSERT…SELECT 血缘；schema 分层 | 表名前缀 `ods_/dwd_/dws_/dim_/*_ready_signal` |
| **docker** | service/image/init(一次性)容器/network/volume/port/依赖 | `docker-compose*.yml`(services 块)；`docker/*.Dockerfile`；`docker/*.sh` | `depends_on`、`networks`、端口映射、`volumes` 挂载 | compose key(services/networks/volumes)；`*-import/*-setup` 命名→init 容器 |
| **python** | service·node/DDD 层/middleware/router·endpoint/值对象·实体 | `main.py`(router 注册段)；`src/**/`(目录树)；`pyproject.toml` | import 关系；`include_router()`；DDD 目录 domain/application/infrastructure | 目录层名(domain/app/infra/presentation)；`*Middleware`、`*Repository` 命名 |
| **claude-code-plugin** | skill/slash command/MCP server/hook/agent/script | `.claude/skills/**/SKILL.md`(frontmatter)；`.mcp.json`(mcpServers)；`.claude/settings*.json`；`.claude/scripts/` | SKILL.md 的 trigger/触发关系；skill 间 sub-call；MCP server 被哪些 skill 引用 | skill 命名族(如 `mj-sys-{doc,git,n8n,ops,flow}-*`)；`.mcp.json` server type |

> 新域照此加一行：先定**实体类型**，再定**L0 声明源**（最权威的清单文件），最后找**归类杠杆**（命名/目录规律）；L1/L2 挖完仍缺 → L3 HITL。这四行只是已核查的样例，**通用层不为任何一个领域背书具体画法**——领域专属的角色映射 / 范式固化在各自的特化手册里。

## §5 worked example 与适用性矩阵

### §5.1 全局适用性矩阵（项目类型 × 7 图）

跑画像 ⑤"轴/密度判断"时，先查这张**全局矩阵**——它把"哪种项目该画哪几张图"一次性摊开，避免逐图 pre-check 时才发现图型不适配。★ 越多 = 信息密度越高、越值得做实；✗ = 不适用（强制 pre-check 会拦截，见对应提示词）。

| 项目类型 | Context L1 | Container L2 | Component L3 | Code L4 | Sequence | State Machine | Deployment |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| **运行时服务**（多容器 / 微服务）| ★★★ | ★★★ | ★★ | ★ | ★★★ | ★★ | ★★★ |
| **单体应用 / 单实例**（如 in-DB 管线）| ★★ | ★★ | ★★★ | ★ | ★★★ | ★★★ | ★ |
| **库 / SDK / framework** | ★ | ✗ | ★★★ | ★★ | ★ | ★ | ✗ |
| **CLI 工具（无 daemon）** | ★ | ✗ | ★★★ | ★ | ★★ | ★ | ✗ |
| **插件市场 / 工具集合** | ★★★ | ✗ | ★★ | ✗ | ★ | ★ | ✗ |
| **静态文档站 / 内容仓库** | ★★ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **IaC / 配置仓库** | ★ | ✗ | ✗ | ✗ | ★（apply 流程）| ★ | ★★★（目标系统）|

读法与三条铁律：

- **✗ 列对应各提示词的 pre-check 拦截点**：对库 / CLI / 插件市场 / 文档站画 Container 或 Deployment 图，会被对应提示词的 pre-check HITL 拦下并建议改图类型——本矩阵是那些 pre-check 的**全局汇总视图**，不替代它们。
- **缩放轴被"压扁"是常态**：单实例 / 单体项目的 L1/L2 信息密度低（系统就一个边界），价值集中在 L3 组件、行为轴（时序 / 状态机）；这类项目主画 Component + Sequence + State Machine。
- **高密度才做实，低密度轻量或略**：★ 单星的图可画可不画，按评审需要定；★★★ 是该项目类型的"必画"骨架。

> 矩阵是**通用判断起点**；具体领域可在其特化手册里据本域实证微调星级（如某 in-DB 管线把 Deployment 进一步降为单机一图）。

### §5.2 worked example（领域样例索引）

§2–§4 的六类画像如何在一个真实领域里被反推出来，属于**领域特化手册**的内容，不在通用层展开——通用层只保证"机制成立"，不为某个领域的具体画法背书。

一份成熟的领域特化手册（即 §7 配方的成品形态）应包含：

1. **① 实体→角色→形状映射表**：该域所有实体类型 → 角色 → 固定 Mermaid 形状 + «stereotype»；哪些实体不作节点而作边标签。
2. **② 连接件线型约定**：该域的边读作什么、用哪种线型（遵循方法论 §5 各图边语义）、边标签承载什么。
3. **③ 自动归类杠杆 + 机检规则**：命名前缀 ↔ 角色 ↔ 形状的一致性，可被 linter 校验。
4. **④ L0 源清单（带 `file:行号` 证据格式）**：该域最权威的声明 / 配置文件 glob。
5. **⑤ 本域适用性微调**：在 §5.1 全局矩阵基础上，按本域实证调整星级。
6. **⑥ 双标签身份源 + 领域范式**：规范 id / 业务别名取处；该域"必须这么画"的复发机制清单。

> 跑完画像 ①–⑥ 并据此沉淀，该域 7 张图的输入即齐。具体样例（如某 PostgreSQL in-database ETL 管线的完整画像反推）由该领域的特化手册承载，与本通用文档解耦。

## §6 命名规范（图名 + slug）—— 唯一事实源，7 张图提示词共用

> **本节是图名 / slug 命名规范的唯一事实源**。方法论 §4.2 给出命名规范的"为什么"（两轴推导、C4/UML 切法、权威先例），并指向本节取可操作规则；七份绘制提示词均引用本节。规则只在此处定义，避免分叉。

每张图名 = `〔轴·层级?〕图型名 [· 变体]` + 一个稳定 kebab **slug**，写进图块**紧跟类型声明行**的两行注释 `%% Name:` / `%% Slug:`（骨架/模板块标 `%% Template` 免检）。**禁不透明序列码**（图1 / A2 / D3）；图名即透出"轴·层级·内容"。

**两段式规则**：

- **轴**：`结构`（缩放轴）/ `行为`（正交）/ `物理`（正交）/ `运行态`（非标准扩展，须显式标「非 C4」）。
- **层级**：**仅结构缩放轴带** `L1/L2/L3/L4`；正交轴（行为/物理/运行态）横穿 L1–L3，**无层级**（依据见方法论 §四「Dynamic / Deployment 是正交视角」）。

**通用 slug 基词表（规范 7 类）**：

| 轴 | altitude | 规范图名 | slug 基 | 4+1 视图 | 提示词文档 |
|---|---|---|---|---|---|
| 结构 | L1 | 系统上下文图 | `struct-l1-context` | Scenarios + Logical | `context-diagram.md` |
| 结构 | L2 | 容器图 | `struct-l2-container` | Logical + Development | `container-diagram.md` |
| 结构 | L3 | 组件依赖图 | `struct-l3-component` | Development | `component-diagram.md` |
| 结构 | L4 | 代码图（罕见手绘）| `struct-l4-code` | Development | `code-diagram.md` |
| 行为 | — | 时序图 | `dyn-sequence-<用例>` | Process | `sequence-diagram.md` |
| 行为 | — | 状态机图 | `dyn-state-<owner>` | Logical + Process | `state-machine-diagram.md` |
| 物理 | — | 部署图 | `phys-deployment-<env>` | Physical | `deployment-diagram.md` |

- **变体后缀**：总览取基名，下钻加 `·overview` / `-<scope>` 变体（借 DFD 分级）；正交轴的 `<用例>` / `<owner>` / `<env>` 段转 kebab 填入。
- **稳定性**：slug 与渲染解耦，作交叉引用与机检锚点——须**显式给定**（自动生成的 key 不保证稳定）。

**落图机制（Mermaid）**：图名与 slug 写进每个图块**紧跟类型声明行**的两行注释——

```text
flowchart TB
  %% Name: 〔结构·L3〕组件依赖图
  %% Slug: struct-l3-component
  ...
```

- **领域可特化（通用 hook）**：领域手册可在本规范上特化——(a) 把轴名改成领域名、(b) 定义本领域的 slug token 词表、(c) 增加非标准扩展轴 / 视图（须显式标「非 C4」）、(d) 加 linter 机检。**通用层本身保持领域无关，不内嵌任何具体领域的 token**；某领域如何把"行为"轴改名、新增扩展轴并机检，固化在该领域自己的特化手册里（沉淀配方见 §7）。

## §7 作者配方：给一个新领域产出"特化"（可选沉淀成手册）

1. **选域 + 定 L0 源**：该域 source-of-truth 在哪（§4 找同类或新加一行）。
2. **跑 L0→L1→L2**：枚举实体 → 推关系 → 命名归类，全程记 `file:行号` 证据。
3. **填 §2 六类画像**：角色→形状表 + 连接件线型 + 归类杠杆 + 信息源 + 密度判断 + 双标签/范式。
4. **L3 HITL 补缺**：只问源里读不出的（同步/异步、可达性、HITL 卡点、为什么）。
5. **挑图**：按 ⑤ 密度判断决定画哪几类（高密度做实，低密度轻量/略）。
6. **逐图套提示词**：拿同目录对应 `*-diagram.md`，用 ③ 的角色映射 + ④ 的事实 + §6 命名出图。
7. **（可选）沉淀**：该域复用频繁时，把 ③④⑥ 沉淀成一份该域"特化手册"——固化角色→形状映射、L0 源清单、命名 token 与领域范式（手册应包含的内容清单见 §5.2）。
