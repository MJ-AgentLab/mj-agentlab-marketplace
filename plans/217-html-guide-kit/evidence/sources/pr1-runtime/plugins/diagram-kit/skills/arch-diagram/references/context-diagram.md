# Context Diagram — 系统上下文图绘制

> 〔命名规范见 `domain-acquisition.md` §6〕规范名 **〔结构·L1〕系统上下文图**；slug `struct-l1-context`（多系统时加 scope，如 `struct-l1-context-<系统>`）。每张图须紧跟类型声明行落 `%% Name` / `%% Slug`（见骨架）。

## 框架定位

- **4+1 视图**：Scenarios + Logical（仅业务入口场景；运行时关键场景另见 Sequence 图）
- **C4 层级**：Level 1
- **主要受众**：老板 / 业务方 / 合规审查 / 安全评审 / 新人 / 跨团队对接方
- **使用场景**：立项 kickoff、合规审查、招标 RFP、新人 onboarding 第一张图

**关于 Scenarios 视图的承担方式**：本图只承担"**业务入口场景**"——主用户/外部系统如何接触系统。运行时关键场景（异常流、超时、并发、降级）应**各开一张专项 Sequence 图**。场景驱动的设计追溯由 ADR 或测试用例承担。Context 图过载承担 Scenarios 全部职责会失去验证视角。

## 必含元素

1. 你的系统：作为一个**不可分割的整体**出现（一个圆形节点，对应 Mermaid `(( ))` 语法）
2. 所有外部用户角色：人类用户、运维、合规员、跨团队对接人
3. 所有外部依赖系统：第三方 API、其他团队的服务、监管接口、数据源 / 数据目标
4. 系统与每个外部实体之间的交互边（必须带业务语义标签）

## 禁含元素

- ❌ 系统内部的容器（不画数据库、缓存、内部服务——那是 Container 图的事）
- ❌ 部署节点（不画 VPC、VM、Pod、可用区——那是 Deployment 图的事）
- ❌ 时序步骤（不标"第 1 步、第 2 步"——那是 Sequence 图的事）
- ❌ 协议细节（不写 HTTP 状态码、JSON schema、端口号——那是 Container 图的事）
- ❌ 外部系统的内部拆分（"邮件服务"画一个就够，不拆 SMTP / IMAP）

## 边的语义规则

每条边必须标注：

- **业务语义内容**："提交分析查询"、"推送监管报表"、"OAuth 登录"
- **触发模式**：实时 / 每日批量 / 事件触发 / 人工触发
- **可选：通道**（HTTPS / SFTP / 邮件 / 文件 drop），仅在合规 / 安全审查相关时标

### Context 图独有约束（与其他结构 / 流量类图不同）

- 所有边**统一使用实线 `-->`**——**不使用 `-.->` 虚线**，**不使用 `==>` 加粗**
- 原因：Context 图边语义最弱（仅"关系 + 数据交换"层级），区分线型会让读者误读为协议/通信模式差异
- **不需要附 legend**——只用一种线型，差异完全通过标签表达
- 所有语义差异（同步/异步、批量/实时、推/拉）一律走**标签文字**

## 一外部实体扮多角色的画法

实际项目里经常遇到"一个外部实体同时扮演多种角色"——典型例子：GitHub 同时是源码托管 + Actions CI + Issue 跟踪。Context 图**仅允许两种画法**：

**画法 A — 多条全实线边**（推荐节点少、关系语义差异大时）：

```text
flowchart TB
    Sys((你的系统))
    GH[GitHub]

    Sys -->|源码托管, 实时| GH
    Sys -->|Actions CI 触发, push 时| GH
    Sys -->|Issue 同步, 实时| GH
```

**画法 B — 边标签合并**（推荐节点多、密度高时）：

```text
Sys -->|源码托管 + Actions CI + Issue 同步| GH
```

**禁止**：
- 用一条无标签或语义模糊的边代表多个角色
- 使用虚线 `-.->` 区分语义（这是 Container/Component/Deployment 图的做法，**Context 图禁用**）

## Mermaid 输出格式

- 图类型：`flowchart TB`
- **分层布局**：用户/参与者在上，系统居中，外部系统在下；**系统是语义焦点而非视觉中心**——视觉位置允许灵活，但语义上所有边都收敛到系统节点
- 用户角色：`[👤 角色名]`
- 你的系统：`((系统名))`（双括号视觉区分）
- 外部系统：`[系统名]`
- 外部数据源：`[(数据源)]`
- 所有边带标签：`A -->|业务语义 + 触发模式| B`
- **图名与 slug**（命名见 `domain-acquisition.md` §6）：紧跟 `flowchart TB` 落 `%% Name: 〔结构·L1〕系统上下文图` / `%% Slug: struct-l1-context`
- **不使用 `graph` 关键字**——它是 Mermaid 早期别名，统一用 `flowchart`

## 自检清单

输出前在内部跑一遍，✗ 项必须修正或在元信息里解释：

- [ ] 你的系统是否只画了一个核心节点，没有展开内部？
- [ ] 所有外部依赖都列了？（LLM API、CDN、监控、监管接口、第三方 SaaS 容易漏）
- [ ] 每条边都有标签？标签是业务语义，不是协议细节？
- [ ] **所有边都是实线 `-->`**？没有错用 `-.->` 或 `==>`？
- [ ] 顶层语法是 `flowchart`（不是 `graph`）？
- [ ] 图块紧跟类型声明行有 `%% Name:` / `%% Slug:` 两行（命名见 `domain-acquisition.md` §6）？
- [ ] 一个非技术读者能在 60 秒看懂吗？
- [ ] 节点总数 ≤ 12？（多了就该合并外部依赖或拆图）

## 输出骨架模板

````text
flowchart TB
    %% Name: 〔结构·L1〕系统上下文图
    %% Slug: struct-l1-context
    User[👤 主要用户角色]
    Admin[👤 运维/管理员]

    Sys((你的系统))

    Ext1[外部系统 1]
    Ext2[外部 API 服务]
    DataSrc[(外部数据源)]

    User -->|主要业务交互, 实时| Sys
    Admin -->|配置/审计| Sys
    Sys -->|调用类型, 实时| Ext1
    Sys -->|API 调用, 实时| Ext2
    DataSrc -->|每日批量推送| Sys
````

## 信息获取要点（针对本图）

> 获取阶梯（L0 声明扫描 → L1 结构推断 → L2 命名归类 → L3 HITL）定义见 `domain-acquisition.md` §3；下方「Layer 0 重点抽」即本图型的 L0 源清单。

**Layer 0 重点抽**：
- `README.md` 顶部：项目简介通常提到主要用户和核心依赖
- `requirements.txt` / `package.json`：识别 LLM SDK、监控 SDK、第三方 SaaS SDK → 外部依赖
- `.env.example` / `config/*.yaml`：第三方服务端点 → 外部依赖

**典型 HITL 问题**（仅当上述挖不到时）：

```
Q1（开放结构化）：列出主要外部依赖，每行一个。
   容易漏：CDN、监控/日志平台、SSO、监管接口、数据出境目的地。

Q2（开放带示例）：主要用户角色是？
   （例：业务分析师、合规员、外部 API 调用方）

Q3（混合）：是否有"系统主动推数据出去"的场景？
   (a) 没有 (b) 有。如有，推到哪里、什么频率？___
```
